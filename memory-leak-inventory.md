## Pointer-Removal Game Plan

- **Prefer value semantics.** Most entities (`Car`, `Truck`, `Garage`, `CarPark`, `Human`) are movable/copyable. Store them directly inside `std::vector` instead of `std::vector<T*>`. Expose references or indexes when other subsystems need access.
- **Adopt smart pointers for polymorphic ownership.** Where polymorphism is essential (e.g., storing heterogeneous `Vehicle`s), use `std::unique_ptr<Vehicle>` and move them into containers. Factory helpers should return smart pointers or concrete objects, never raw `new`.
- **Eliminate manual `new[]`.** `char*` license plates can be plain `std::string` (or `std::array<char, 7>`). Replacing them removes the need for explicit deletes and avoids copying errors.
- **Add destructors only when still needed.** After migrating to values/smart pointers, most classes can rely on compiler-generated destructors. If a class truly owns a legacy raw pointer, implement a destructor plus copy/move semantics so ownership stays clear.
- **Audit helper collections.** Logging/history buffers (`auditTrail`, `exitHistory`, etc.) should either cap their size or store by value to keep the memory tracker quiet. Consider wrapping these in RAII structs that release resources automatically.

Applying these steps will bring `MemoryTracker`’s `outstanding_allocations` counter back to zero at shutdown and makes future leak hunting much easier.
